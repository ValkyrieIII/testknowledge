# 前端改正计划

> 背景：提取管线完成"证据 / 观测 / 知识"三层拆分并新增运行台账后，前端没有跟着动。
> 渲染组件本身**不需要重构**——实测 LLM 生成的卡片在现有卡面上字段全部正确填充。
> 要改的是"**显示什么**"：一个区块显示着已经搬走的数据，一个新层没有任何显示，
> 一个判据漏掉了新生产者，一整块新能力没有界面，半边审核逻辑在空转。

---

## A. 默认视图漏掉新生产者（1 行，最高优先）

**问题**

`apps/web/src/App.vue:35` 默认 `knowledgeView = "agent_candidates"`，`:41` 的判据是：

```ts
if (view === "agent_candidates") return card.status === "candidate" && card.proposalProvenance.source === "agent";
```

`agent` 只匹配早期人工/agent 起草的卡。LLM 产出的卡 `source === "llm_extractor"`，
**在默认视图里一张都不显示**。实测（qqbot，93 张可见卡）：

| 视图 | 显示 | 其中 LLM 卡 |
|---|---|---|
| 当前 Agent 待审（默认） | 14 | **0** |
| 全部待审 | 48 | 34 |

**改法**

默认视图改为按**状态**过滤（`status === "candidate"`），而不是按"谁写的"。
`llm_extractor` 与 `agent` 都是机器起草的候选，没有理由在默认队列里被藏起来。

若确实需要保留"来源"这一维度，应作为**独立的筛选器**，而不是拿它当默认视图的隐含条件。

同时需要同步 `:39` 的 `agentCandidateCount` 计数与 `:607` 的说明文案。

**验收**：打开页面默认即可见 34 张 `llm_extractor` 候选卡。

## B. `候选来源` 打印裸英文（几行）

**问题**：`KnowledgeCardView.vue:142` 直接输出 `{{ card.proposalProvenance.source }} · {{ card.proposalProvenance.actor }}`，
在新卡上显示为 `llm_extractor · extractor.llm.behavior-v2`。
kind / status / technique 都做了中文映射表，provenance 漏了。

**改法**：新增一张映射表，与既有 `kinds` / `statuses` / `techniqueNames` 并列：

```ts
const provenanceNames: Record<ProposalProvenance["source"], string> = {
  deterministic_extractor: "规则抽取", llm_extractor: "语义抽取",
  human: "人工录入", agent: "Agent 起草", unknown: "来源未记录",
};
```

**验收**：卡面显示中文来源，`actor` 作为附注保留（它对审计有用，不要删）。

## C. `OBSERVED FACTS` 区块恒为空（删除并迁移）

**问题**：`KnowledgeCardView.vue:32-43` 与 `:104-137` 读取 `card.observed`。
规则抽取器不再产出知识卡、LLM 的 `toDraft` 也不写这个字段，
因此**每一张卡都显示"未记录结构化事实"**——一整块常驻占位符。

**关键判断**：这些事实**没有消失**。按三层设计，它们属于**观测层**——
是**按查询计算的**投影，不是卡片自身的属性。所以正确做法不是"补上 card.observed"，
而是**把这块从卡上移除**，数据在检索结果面板展示（见 D）。

**改法**

1. 删除卡面上的 `observed-facts` 区块、`fields` / `facts` 两个 computed，以及其他文件里对 `card.observed` 的引用。
2. 若为兼容旧数据想保留，也不应显示为卡片字段——它会诱导读者以为"这张卡自带这些事实"。

**验收**：卡面不再出现恒空的"未记录结构化事实"。

## D. 观测层没有渲染（新界面，中等）

**问题**：`ContextPack.observations` 已经存在（阶段二加的），
但检索结果区（`App.vue:429-547`）只渲染 `knowledge` / `abstentions` / `executionSignals`。
**一个完整的新层在界面上看不见。**

**改法**：照抄同一区里 `关联执行信号`（`:489-516`）的折叠模式，加一块**机械事实**：

- 摘要行加一项：`· N 条机械事实`
- 折叠块：`<summary>机械事实（N 条）</summary>`
- 内部按 `Observation.kind` 分组（fixture / mock / assertion / exception / parametrization /
  lifecycle / environment / test_location / dependency / run_instruction / history），
  组内逐条列出 `statement`
- 每条附 `sourceRef` 与行号 `lineStart–lineEnd`；`evidenceIds` 复用现有 `<EvidenceDetails>`
- 中文标签与卡面的 `kinds` 风格保持一致

**注意**：观测**不落库**（查询时算）。验收时要同时确认 `knowledge.jsonl` 行数不变。

**验收**：查询后可见机械事实（qqbot 实测 16 条），且数据文件中无新增行。

## E. 运行台账没有入口（新界面，中偏大）

**问题**：`GET /api/runs` 与 `GET /api/runs/:id/items` 已就绪，界面零渲染。
而"15 个分片里哪几片失败、为什么"恰恰是本轮最有说服力的证据——现在只能开命令行敲 `runs`。

**改法**：在 `03 / KNOWLEDGE` 区新增一个可折叠块（或独立 section，建议新增
`components/RunLedgerView.vue` 以免 `App.vue` 继续膨胀）：

- 运行列表：`stage`、`disposition`（done / failed / **skipped** 三种）、`durationMs`、`counts`
- 展开某次运行 → 逐条目的 `itemKey` / `disposition` / `errorCode` / `errorMessage`
- 失败条目标红；`errorCode` 做中文映射（timeout / http_4xx / http_5xx / parse / unknown）

**必须注意的一点**：条目记录目前是**按阶段批量落盘**的，
因此**长阶段执行期间这里会显示为空**。不要把它做成"实时进度条"——那会误导。
两个选择：在界面上写明"阶段结束后可见"，或先把批量写改成增量刷（后端改动，另议）。

**验收**：可见 `behavior:tests#2`、`behavior:tests#4`、`historical_bug:.git#1` 三条失败及其原因。

## F. 分组 UI 空转（本次不修）

`clusterId` 永远为空——簇层 100% 被拒（确定性信号词表只覆盖测试代码字段）。
因此"分组"行不显示，审核按钮上 `clusterStatus !== 'reviewed'` 的门禁也永不触发。

这与后端"簇层结构性失效"是同一件事，**等后端修好再动 UI**，现在不要为它做界面。

## 顺序与验收

**建议顺序**：A → B → C+D → E。

- A / B 是一两行，直接决定"打开页面能不能看到东西"
- C+D 是一次数据结构迁移（从卡片属性搬到查询面板）
- E 是新界面

**统一验收方式**：用**副本数据根**跑，不要动真实库

```bash
cp -r .testknowledge /tmp/tk-ui && TESTKNOWLEDGE_DATA_ROOT=/tmp/tk-ui node apps/api/dist/main.js
cd apps/web && npx vite --port 5173     # 代理到 127.0.0.1:4173
```

逐项确认：

1. 打开页面默认即见 `llm_extractor` 的 34 张候选卡
2. 卡面来源显示中文，不再出现恒空的 `OBSERVED FACTS`
3. 查询后出现"机械事实"区块，且 `knowledge.jsonl` 行数不变
4. 台账区块能看到三条失败分片及原因
5. `pnpm --filter @testknowledge/web build` 通过
6. 既有的状态筛选、计数、审核、回滚功能无回归

## 明确不做

- 卡片渲染组件不重构——实测 LLM 输出与现有卡面结构兼容
- 不为"分组"做界面（F）
- 不把台账做成实时进度条（E 的注意事项）
