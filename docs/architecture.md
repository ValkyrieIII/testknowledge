# TestKnowledge 架构

> 目标:给 Coding Agent 提供**项目特有的测试知识**,让它在写测试时少踩已经踩过的坑。
> 本文是收敛后的架构设计。讨论过程中的开放问题见 `docs/framework-discussion.md`。

日期:2026-09-12

**已实现并启用**

- 证据卡(**测试函数级**):`observed` 结构化事实(断言 / 期望异常 / mock / factory / 依赖 / 参数化)

- API / CLI / Web

- 持久化测试项目地图：生产/测试文件、配置、环境、符号、fixture 与证据化运行指令，并注入 Context Pack

- 有类型关系持久化：`SUPPORTED_BY`、`USES_FIXTURE`、保守的 `COVERS`；有直接断言/期望异常才生成 `VERIFIES`，且不等同于生命周期 verified
- 可替换 `StructuralContextProvider`：通过 CodeGraph JSON 接口提供任务期 `IMPACTS` 和相关路径

- 显式外部快照适配：仓库内 Issue JSON 与 CI/测试结果 JSON 进入证据层；执行结果结构化保留用例计数、覆盖率、变异指标和失败明细；不联网、不执行、不自动验证

- 证据绑定的人工知识卡录入与显式冲突治理；冲突知识默认不进入 Agent 上下文
- 单修订人工知识包导入：整包先校验证据和重复身份，再单次更新卡片、关系、索引和操作级审计
- 人工合并、全量来源证据保留、`MERGED_FROM` 关系、操作级版本审计与可恢复回滚；合并和回滚均重新进入 candidate
- v2 冻结式 A/B/C 行为评估：完整提示策略、逐变体工具白名单、预算及私有评分口径参与哈希，运行清单按 `runSetId` 为每个任务/变体生成确定性运行身份和 `runSpecHash`；反馈、观察及报告必须绑定同一批次、实际工具/成本和规格，分别统计无效断言、重复与脆弱测试，确定性输出增益或证据不足
- 评测观察按 `runId` 不可变；相同请求幂等返回，修改或重跑必须使用新 `runSetId`，避免事后覆盖结果
- Web 评估面板：并列展示冻结条件、A/B/C 样本完整度、行为指标、成本变化与判定理由
- Web 关系视图：按仓库呈现关系类型、两端节点、证据数量、来源、置信度和冲突决议
- Context 编译器执行语言、框架、版本、目标符号和目标路径适用性硬过滤
- 双通道失效检测：证据语义指纹忽略纯行号移动，支撑证据、唯一目标函数、mock 目标、fixture 或 pytest 环境配置变化会使已审核知识 stale 并清空旧验证；显式 Oracle 反证反馈则保留历史验证链，新增 `INVALIDATED_BY` 反例关系和审计快照
- 独立 stdio MCP 适配层；`get_test_context` 为聚合入口，协议层不反向依赖核心
- API、CLI、MCP 共用一个可注入的 composition root；默认 repository、索引、Source Adapter、抽取器、CodeGraph 和 Git provider 只注册一次，协议入口不能各自漂移
- 独立 `EvidenceCluster` 资产：LLM 只提议，核心校验证据引用和组内共享信号，分组与卡片分别人审
- 有限 `techniques` 词表：规则只标确定性可识别手法，LLM 输出必须通过枚举校验
- 多框架发现与适配：pytest 保留配置感知的专用发现；Java/JUnit、Go testing、Rust test 分别注册独立保守词法适配器并共享内部词法工具，统一输出 Evidence，不把生命周期钩子误当成可注入 fixture
- 多 Agent 接入：Codex 使用项目级 TOML，Claude Code 与 Copilot CLI 共享仓库级 `.mcp.json`，VS Code Copilot 使用工作区配置；各端只替换 MCP 客户端配置，不复制知识核心，云端 Copilot 仍需独立部署远程 MCP
- QQBot 阶段一试点：固定仓库修订静态抽取 260 条 Evidence，导入 14 张高价值人工候选卡，并验证默认安全回退与显式候选精确召回；行为增益仍待隔离 A/B/C 执行证明

**已实现、显式启用**
- `LlmKnowledgeExtractor`：仅在请求 `useLlm` / `--llm` 且三个环境配置完整时运行；输入是截断的确定性证据，输出始终为候选，失败回退规则抽取

## 1. 定位

**做什么**:从项目的测试代码里提炼「测试设计知识」,让 Agent 在写新测试时能复用。

**不做什么**:不做通用代码知识(架构文档、技术栈)。那是 Qoder 等工具的位置;它们的三类知识卡里没有「测试」。

**输入 → 输出**:

```
一个项目 → 抽取证据 → 聚合成知识 → 人工审核 → Agent 查询时注入
```

---

## 2. 核心原则

| 原则 | 含义 |
|---|---|
| **确定性优先** | 代码是形式化的,能被精确解析。确定性层负责事实,LLM 只补它补不了的 |
| **精度优先于召回** | 漏掉一张该给的卡 = 退回普通 Agent(可接受);给错一张 = Agent 可能信了(有害)。宁可说「没有」 |
| **必须有出处** | 每条知识能指到具体文件、行号、代码片段 |
| **LLM 不判定孤立事实** | 事实由确定性层产出。LLM 只能对「已确定的事实」提出**结构化提议**(分组、措辞)，提议必须通过确定性校验和人审 |
| **人审 + 可执行验证** | 人审判「该不该有」,执行验证判「断言有没有用」 |

## 3. 核心分工

```
① 确定性：抽证据        测试函数 → 断言/异常/mock/依赖/参数化（带行号）
        ↓
② LLM：提议分组         哪些证据在说同一件事 → 候选簇（必须引用证据 id）
        ↓
③ 确定性：校验提议      引用存在吗？组内是否共享确定性信号？
        ↓
④ LLM：写知识           每簇 → 一句行为描述 + 从词表选手法 + 引用证据 id
        ↓
⑤ 确定性：校验          引用的证据存在吗？说的话超出证据了吗？
        ↓
⑥ 人：审核             分组对不对 + 卡片对不对 → candidate / reviewed
        ↓                  全部支撑证据必须仍属于当前项目修订
⑦ 外部执行 + 人确认      reviewed + 同修订 passed 证据 → verified
```

**关键**:
- LLM 只做两件不可替代的事:**提议分组**和**写措辞**。
- 它的输入是**确定性层产出的证据**,不是原始代码。
- 它的输出是**候选提议**,必须过确定性校验 + 人审——所以不是「猜」,是「提议」。
- 生命周期不允许绕过治理：`rejected` 需要重写为新候选；验证只能从 `reviewed` 出发，且必须引用与卡片同修订、显式绑定并通过的执行证据。失败不自动否定 Oracle；只有同仓库、同修订、显式绑定卡片且带评估人和说明的 `contradicted` 评估，才能把 `reviewed`/`verified` 降为 `stale` 并触发重新评审。

> **②与④均已可显式启用。** 默认继续走确定性规则出卡；只有配置完整并由 API `useLlm: true`
> 或 CLI `build --llm` 明确请求时，才提议证据分组并生成行为级候选卡。

## 5. 数据模型

### 5.1 Evidence(已有)

一条原始事实 + 出处。

```
{ id, sourceType, path, symbol, lineStart, lineEnd, contentHash, payload }
payload: { assertions, withBlocks, tryHandlers, decorators, parameters, mocks, calls, ... }
```

### 5.2 EvidenceCluster(显式启用)

只有启用 LLM 抽取时才产生候选簇。核心层会拒绝不存在的证据引用、少于两条证据的簇，以及没有
共享确定性信号的簇；通过校验仍只是 `candidate`，需要独立人审。

```
{
  id,
  subject,          // 被测对象，如 "get_key"
  shape,            // 断言形状，如 "returns_none"
  evidenceIds: [],  // 成员证据
  sharedSignals: [],// 核心重新计算的断言形状 / 调用参数 / 前置信号
  repo, revision, confidence, status, extractor
}
```

### 5.3 KnowledgeCard(当前形态)

默认规则抽取仍形成**函数级证据卡**；显式 LLM 流程可以形成引用已校验簇的行为级候选卡。
`observed` 是结构化事实,`statement` 是它的短句渲染。

```
{
  id, clusterId?,            // 内容寻址；行为级卡可引用独立分组
  origin, proposalProvenance,// 录入方式与实际候选起草来源分开记录
  kind,                      // fixture | behavior | assertion | ...
  title,
  statement,                 // 短句，如 "断言：result is None；依赖：tmp_path"
  observed: {                // 结构化事实
    assertions, expectedExceptions, mocks, dependencies, parametrize
  },
  oracle, trigger, expectedBehavior, risk,
  repo, revision, path, symbol,
  evidenceIds,
  confidence, status, sourceHash, createdAt, updatedAt
}
```

**已加入但仍保守**:`applicability` 目前由 Python/pytest 确定性来源填写语言、框架、路径、符号与版本；尚未用于跨项目迁移。
**已加入**:`techniques` 使用有限枚举；`validationEvidenceIds` 单独记录执行验证证据。
**溯源边界**:`origin: manual` 只表示通过治理入口录入；`proposalProvenance` 才表达候选由规则、LLM、人或 Agent 起草，导入不会冒充人工审核。
**粒度**:默认是测试函数级；显式 LLM 流程是行为级。分组审核通过前，对应知识卡不能审核或验证。

## 6. 测试设计手法词表(已实现,有限)

规则抽取只在结构事实足够明确时标注手法，例如参数化、边界字面量、预期异常、fixture、mock、
相等断言、Hypothesis 装饰器、快照调用和并发调用。LLM 只能从同一枚举中选择；未知值会使候选卡
被拒绝，而不是扩充词表。

手法是有限集合,由人定稿。初版约 15 个:

| id | 名称 | 定义 |
|---|---|---|
| `boundary_value` | 边界值 | 测边界输入(0、1、最大、空) |
| `equivalence_partition` | 等价类 | 输入分组,每组取代表 |
| `parameterized_input` | 参数化输入 | 同一逻辑跑多组输入 |
| `exception_path` | 异常路径 | 验证抛出预期异常 |
| `error_handling` | 错误处理 | 验证错误被捕获/降级 |
| `dependency_isolation` | 依赖隔离 | mock/patch 外部依赖 |
| `fixture_injection` | 前置注入 | 复用项目 fixture 做前置 |
| `round_trip` | 往返 | 编码→解码后相等 |
| `state_transition` | 状态转换 | 验证状态机迁移 |
| `ordering` | 顺序依赖 | 验证顺序相关行为 |
| `idempotence` | 幂等 | 重复执行结果不变 |
| `property_based` | 属性测试 | 对一类输入验证不变量 |
| `snapshot_regression` | 快照/回归 | 与基线快照比对 |
| `concurrency` | 并发 | 验证并发下行为 |
| `equivalence_assertion` | 等价性断言 | 结果与期望精确相等 |

**用法**:规则与 LLM 共用这个表；选不出来就不标。手法进入 JSONL、检索文本、Web 展示和 verified 导出。

## 7. 惯用法识别(不让 LLM 猜)

问题:`with pytest.raises(E)` 和 `with open(f)` 语法一样,含义藏在**名字**里,而名字是无限的。

分三层处理,全部确定性:

```
① 语法层      assert / try-except          → 手法（认节点，不需要名字）
② 框架词汇表   pytest.raises / parametrize  → 手法（数据表，有界）
③ 读定义      自定义 check_equal 的函数体    → 手法（以后做）
④ 认不出      不标（不猜，精度优先）
```

**「读定义」是可选的基建**:它让项目自定义的 helper 能自动识别。不做也行,只是这类 helper 不产卡。

## 8. 关键机制

### 8.1 分组(显式启用)

#### 方案:LLM 提议 + 确定性校验 + 人审

**为什么不用纯规则**(已实测):

确定性指纹只有两个极端——

- **保守**:29 个测试 → 25 簇,几乎没合(等于没做)
- **激进**:29 → 17,但把 `test_load_dotenv_existing_file` / `_no_override` / `_override` 三个**不同规则**错合成一簇

「是不是同一个行为」是语义判断,表面特征抓不住。所以改成:

| 步骤 | 谁做 |
|---|---|
| 提议「哪些证据是一组」 | **LLM**(输入是确定性证据,必须引用 id) |
| 检查「组内是否共享确定性信号」 | 确定性校验(断言形状 / 调用参数 / 前置) |
| 检查「引用的证据是否存在」 | 确定性校验 |
| 最终「这个分组对不对」 | **人审** |

**LLM 提的是「候选分组」,不是结论。** 校验不过或人不认,就打回。

当前核心对每个候选簇重新计算共享信号，只接受至少两条同仓库、同版本证据，并要求所有成员共享
断言形状、带字面参数的调用、预期异常、fixture 前置或 mock 目标中的至少一种。分组拒绝时，其关联
知识卡一并拒绝；分组通过不会自动通过知识卡。

### 8.2 LLM 约束

| 约束 | 做法 |
|---|---|
| 只能引用已有证据 | 输出必须带 evidenceIds;校验层检查存在性 |
| 只能从词表选手法 | 输出用 enum 约束 |
| 不能编事实 | 核心检查目标符号、路径、依赖及显式代码/错误码锚点是否逐项出现在所引证据中；不满足则整卡拒绝 |
| 结果稳定 | 簇按 repo + subject + shape + evidenceIds 内容寻址；模型响应按抽取器、端点、模型、参数和证据消息内容寻址，使用不可变文件缓存 |

### 8.3 卡片身份

内容寻址:**repo + 语义字段**(不含 revision / evidenceIds / confidence)。
→ 改无关文件不会让已审核的卡失效。

## 9. 分期

| 阶段 | 内容 | 依赖 LLM |
|---|---|---|
| **1** | 项目接入 + 函数级证据卡 + 界面（**不分组、不接 LLM**） | ❌ |
| **2** | LLM 分组提议 + 确定性共享信号校验 + 行为级候选卡（显式启用） | ✅ |
| **3** | 读定义 / 迁移 / 可执行验证 | 视情况 |

**当前阶段 1 已具备完整数据与治理入口；阶段 2 已具备独立分组资产、确定性校验、双重审核门槛，以及人工合并与可回滚版本审计。阶段 3 已接入 CodeGraph、Git 历史和外部执行反馈，但受控隔离执行器与跨项目迁移仍未实现。**

**阶段 1 纯确定性,能独立演示、独立测试。分组从阶段 2 开始(需要 LLM)。**

## 10. 仍待验证或决策的边界

1. **适用条件的粒度**:当前支持语言、框架、路径、符号和版本硬过滤；是否加入更细业务场景，待试点评估。
2. **迁移粒度**:跨仓库 / 跨框架 / 跨语言?
3. **界面展示**:已有知识、证据、关系、治理和评估视图；是否展示逐步抽取过程，取决于真实排障需求。
4. **「读定义」做不做**:取决于完整语法解析后仍未识别结构的占比。
5. **可执行验证怎么落地**:已支持外部隔离结果、覆盖率和变异数据回写；仓库内受控 runner 仍需单独授权和安全设计。

| Evidence | 从代码里抄下来的原始事实 + 出处 |
| 证据簇 | 由 LLM 提议、核心校验共享信号并独立人审的一组行为证据 |
| 手法 | 测试设计技术(边界值、异常路径……),有限词表 |
| 惯用法 | 框架/团队给代码起的特殊名字(`pytest.raises`、`check_equal`) |
| 适用条件 | 这张卡在什么语言/框架/场景下成立 |
| 迁移 | 把一张卡用到别的项目/场景 |
| 可执行验证 | 把代码故意弄坏,看卡的断言能不能抓住 |

## 12. 决策记录

| 日期 | 决策 | 理由 |
|---|---|---|
| 2026-09-09 | 分组由 **LLM 提议 + 确定性校验 + 人审**,不用纯规则 | 实测纯规则两头不讨好:保守(29→25)等于没做;激进(29→17)把 override 三个不同规则错合 |
| 2026-09-09 | LLM 只对「已确定的事实」提提议,不判定孤立事实 | 防编造;提议必须可校验、可人审 |
| 2026-09-09 | 惯用法识别:语法层 + 框架表;读定义可选;认不出不标 | 不让 LLM 猜 |
| 2026-09-09 | 阶段 1 不分组,先做函数级卡片 + 手法标签 | 分组需要 LLM,且不是当前瓶颈 |
| 2026-09-09 | 规范词表暂不引入;LLM 只从现有证据生成行为卡 | 先验证「证据 → 行为卡」这条链路,词表晚一步 |
| 2026-09-09 | **LLM 抽取暂时停用**(接线注释),默认走确定性规则出卡 | 实测 LLM 只看到派生事实、看不到代码片段 → 瞎补细节(如把「裸 key」说成「空值」);先把证据卡做稳 |
| 2026-09-09 | 证据卡加 `observed` 结构化事实,`statement` 变短;`kind` 不再误标 `fixture` | 「断言/异常/mock/依赖/参数化」分字段;`fixture` 只给真正的 fixture 定义 |
| 2026-09-12 | 在 Evidence 具备受控原文后恢复显式 LLM 抽取 | 输入截断、来源视为不可信数据、输出必须引用 Evidence ID，且始终为 candidate；失败回退确定性规则 |
