## 1. 定位

**做什么**:从项目的测试代码里提炼「测试设计知识」,让 Agent 在写新测试时能复用。

**不做什么**:不做通用代码知识(架构文档、技术栈)。那是 Qoder 等工具的位置;它们的三类知识卡里没有「测试」。

**输入 → 输出**:

```
一个项目 → 抽取证据 → 聚合成知识 → 人工审核 → Agent 查询时注入
```

---

## 2. 核心原则

| 原则 | 含义 |
|---|---|
| **确定性优先** | 代码是形式化的,能被精确解析。确定性层负责事实,LLM 只补它补不了的 |
| **精度优先于召回** | 漏掉一张该给的卡 = 退回普通 Agent(可接受);给错一张 = Agent 可能信了(有害)。宁可说「没有」 |
| **必须有出处** | 每条知识能指到具体文件、行号、代码片段 |
| **LLM 不判定孤立事实** | 事实由确定性层产出。LLM 只能对「已确定的事实」提出**结构化提议**(分组、措辞)，提议必须通过确定性校验和人审 |
| **人审 + 可执行验证** | 人审判「该不该有」,执行验证判「断言有没有用」 |

---

## 3. 核心分工

```
① 确定性：抽证据        测试函数 → 断言/异常/mock/依赖/参数化（带行号）
        ↓
② LLM：提议分组         哪些证据在说同一件事 → 候选簇（必须引用证据 id）
        ↓
③ 确定性：校验提议      引用存在吗？组内是否共享确定性信号？
        ↓
④ LLM：写知识           每簇 → 一句行为描述 + 从词表选手法 + 引用证据 id
        ↓
⑤ 确定性：校验          引用的证据存在吗？说的话超出证据了吗？
        ↓
⑥ 人：审核             分组对不对 + 卡片对不对 → candidate / verified
```

**关键**:
- LLM 只做两件不可替代的事:**提议分组**和**写措辞**。
- 它的输入是**确定性层产出的证据**,不是原始代码。
- 它的输出是**候选提议**,必须过确定性校验 + 人审——所以不是「猜」,是「提议」。

> **②④ 目前停用。** LLM 模块已实现,但 `api` / `cli` 未接线;当前默认走确定性规则出卡(**函数级**,不分组)。

## 5. 数据模型

### 5.1 Evidence(已有)

一条原始事实 + 出处。

```
{ id, sourceType, path, symbol, lineStart, lineEnd, contentHash, payload }
payload: { assertions, withBlocks, tryHandlers, decorators, parameters, mocks, calls, ... }
```

### 5.2 EvidenceCluster(未实现)

> **未实现。** 这是「行为级聚合」的载体,随分组方案(8.1)一起暂缓。当前卡片直接对应单个测试函数,没有簇。

```
{
  id,
  subject,          // 被测对象，如 "get_key"
  shape,            // 断言形状，如 "returns_none"
  evidenceIds: [],  // 成员证据
  repo, revision
}
```

### 5.3 KnowledgeCard(当前形态)

**函数级证据卡**。`observed` 是结构化事实,`statement` 是它的短句渲染。

```
{
  id,                        // 内容寻址：repo + 语义字段 + observed
  kind,                      // fixture | behavior | assertion | ...
  title,
  statement,                 // 短句，如 "断言：result is None；依赖：tmp_path"
  observed: {                // 结构化事实
    assertions, expectedExceptions, mocks, dependencies, parametrize
  },
  oracle, trigger, expectedBehavior, risk,
  repo, revision, path, symbol,
  evidenceIds,
  confidence, status, sourceHash, createdAt, updatedAt
}
```

**尚未加入**:`applicability`(适用条件)、`techniques`(设计手法)、`validation`(可执行验证)。
**粒度**:目前是**测试函数级**(一张卡对应一个测试函数);行为级聚合需要分组,见 8.1(**未实现**)。

## 6. 测试设计手法词表(规范,有限)

> **暂不实现,先记录。** 当前卡片是函数级证据卡,不涉及手法词表。

手法是有限集合,由人定稿。初版约 15 个:

| id | 名称 | 定义 |
|---|---|---|
| `boundary_value` | 边界值 | 测边界输入(0、1、最大、空) |
| `equivalence_partition` | 等价类 | 输入分组,每组取代表 |
| `parameterized_input` | 参数化输入 | 同一逻辑跑多组输入 |
| `exception_path` | 异常路径 | 验证抛出预期异常 |
| `error_handling` | 错误处理 | 验证错误被捕获/降级 |
| `dependency_isolation` | 依赖隔离 | mock/patch 外部依赖 |
| `fixture_injection` | 前置注入 | 复用项目 fixture 做前置 |
| `round_trip` | 往返 | 编码→解码后相等 |
| `state_transition` | 状态转换 | 验证状态机迁移 |
| `ordering` | 顺序依赖 | 验证顺序相关行为 |
| `idempotence` | 幂等 | 重复执行结果不变 |
| `property_based` | 属性测试 | 对一类输入验证不变量 |
| `snapshot_regression` | 快照/回归 | 与基线快照比对 |
| `concurrency` | 并发 | 验证并发下行为 |
| `equivalence_assertion` | 等价性断言 | 结果与期望精确相等 |

**用法**:LLM 只能从这个表里选;选不出来就不标。

## 7. 惯用法识别(不让 LLM 猜)

问题:`with pytest.raises(E)` 和 `with open(f)` 语法一样,含义藏在**名字**里,而名字是无限的。

分三层处理,全部确定性:

```
① 语法层      assert / try-except          → 手法（认节点，不需要名字）
② 框架词汇表   pytest.raises / parametrize  → 手法（数据表，有界）
③ 读定义      自定义 check_equal 的函数体    → 手法（以后做）
④ 认不出      不标（不猜，精度优先）
```

**「读定义」是可选的基建**:它让项目自定义的 helper 能自动识别。不做也行,只是这类 helper 不产卡。

## 8. 关键机制

### 8.1 分组(未实现)

> **未实现。** 当前不做分组:一张卡对应一个测试函数。

#### 方案:LLM 提议 + 确定性校验 + 人审

**为什么不用纯规则**(已实测):

确定性指纹只有两个极端——

- **保守**:29 个测试 → 25 簇,几乎没合(等于没做)
- **激进**:29 → 17,但把 `test_load_dotenv_existing_file` / `_no_override` / `_override` 三个**不同规则**错合成一簇

「是不是同一个行为」是语义判断,表面特征抓不住。所以改成:

| 步骤 | 谁做 |
|---|---|
| 提议「哪些证据是一组」 | **LLM**(输入是确定性证据,必须引用 id) |
| 检查「组内是否共享确定性信号」 | 确定性校验(断言形状 / 调用参数 / 前置) |
| 检查「引用的证据是否存在」 | 确定性校验 |
| 最终「这个分组对不对」 | **人审** |

**LLM 提的是「候选分组」,不是结论。** 校验不过或人不认,就打回。

### 8.2 LLM 约束

| 约束 | 做法 |
|---|---|
| 只能引用已有证据 | 输出必须带 evidenceIds;校验层检查存在性 |
| 只能从词表选手法 | 输出用 enum 约束 |
| 不能编事实 | 校验层检查 statement 里的关键实体是否出现在证据中 |
| 结果稳定 | 按簇内容哈希缓存 |

### 8.3 卡片身份

内容寻址:**repo + 语义字段**(不含 revision / evidenceIds / confidence)。
→ 改无关文件不会让已审核的卡失效。

## 11. 术语

| 词 | 含义 |
|---|---|
| Evidence | 从代码里抄下来的原始事实 + 出处 |
| 证据簇 | 在验证同一行为的一组证据(**未实现**) |
| 手法 | 测试设计技术(边界值、异常路径……),有限词表 |
| 惯用法 | 框架/团队给代码起的特殊名字(`pytest.raises`、`check_equal`) |
| 适用条件 | 这张卡在什么语言/框架/场景下成立 |
| 迁移 | 把一张卡用到别的项目/场景 |
| 可执行验证 | 把代码故意弄坏,看卡的断言能不能抓住 |
