> 目的:在动工前把「整体结构」和「实现规划」定下来。本文记录背景、现状、已定原则,以及需要拍板的问题。
> 建议会上逐条过第 5 节的问题,每条选一个方向。

日期:2026-09-09

---

## 1. 目标

导师给出的方向(原文拆解):

1. 先做**可视化界面 + 简单的后端接口**。
2. 给一个**项目**,自动抽取测试知识。
3. 用**大模型**总结「测试用例的设计意图 / 思路」。
4. 抽出来的知识,**下次在别的类似项目 / 场景加载使用**。

核心假设(需要验证):人写的测试代码里蕴含了测试设计思想,这些思想是大模型不容易自己想到的。

## 2. 当前进展

已经能跑通的最小闭环:

```
项目文件 → 解析 → 原始记录(Evidence) → 规则抽取 → 知识卡 → 人工审核 → 检索 → 返回
```

| 层 | 现状 |
|---|---|
| 项目接入 | ⚠️ 需要手动指定文件,不能自动扫项目 |
| 确定性抽取 | ✅ 语法树抽事实(断言/异常/参数/装饰器/调用) |
| 设计信号 | ❌ 未做(把事实映射成「用了什么测试设计手法」) |
| LLM 提炼 | ⚠️ 有骨架,可选、未启用,输出的是「事实」不是「设计意图」 |
| 知识模型 | ⚠️ 是「事实卡」,绑定 repo/path/symbol,不可迁移 |
| 存储检索 | ✅ JSONL 权威 + SQLite 索引 |
| 接口 / 界面 | ⚠️ 有,但简陋 |
| 迁移到其他项目 | ❌ 未做 |

## 3. 已确定的原则

这几条是前面讨论的结论,建议会上确认,之后不再反复:

1. **确定性优先。** 代码是形式化产物,能被精确解析。确定性层负责「事实」,LLM 只负责它不可替代的「语义措辞」,并且输出要能被确定性校验。
2. **精度优先于召回。** 漏掉一张该给的卡 = 退回普通 Agent 判断(可接受的降级);给了一张不该给的卡 = Agent 可能信了它(有害)。宁可返回「没有」,不要返回「可能适用」。
3. **每条知识必须有出处。** 能指到具体文件、行号、代码片段。
4. **人审 + 可执行验证。** 人审判断「该不该存在」,执行验证判断「断言有没有用」。

## 5. 待讨论的问题

### Q1 知识卡的形态是什么?

| 选项 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| A 事实卡 | 「这个测试断言是 X」 | 精确、可追溯 | 绑死仓库,不可迁移 |
| B 设计模式卡 | 「这类场景应该这样设计」 | 可迁移 | 可能模型自己也会,价值存疑 |
| C 两层 | 模式层(可迁移) + 绑定层(出处) | 兼顾 | 结构复杂一些 |

**影响**:决定数据模型、抽取方式、检索方式。
**建议**:C。模式层用于迁移,绑定层用于溯源。

### Q2 适用条件的粒度?

| 选项 | 例子 |
|---|---|
| 只绑仓库 | repo = xxx |
| + 语言 / 框架 | language=python, framework=pytest |
| + 场景模式 | pattern=环境变量加载 |
| + 代码结构 | 函数含 parametrize 且参数是字面量列表 |

**影响**:条件越细越准,但迁移范围越小。
**建议**:语言 + 框架 + 场景,先不做跨语言。

### Q3 LLM 放在哪一层,输出什么,怎么校验?

| 选项 | 说明 |
|---|---|
| A LLM 直接读测试代码总结 | 简单,但不可复现、容易编 |
| B 确定性出信号 → LLM 组织措辞 → 确定性校验 | 可复现、可追溯、成本低 |

**建议**:B。LLM 的每条输出必须引用确定性层产出的证据编号;校验层检查引用是否存在、引用的代码是否真的包含所述行为。

### Q4 迁移的粒度?

| 层级 | 难度 | 现状 |
|---|---|---|
| 同项目内,符号→符号 | 中 | 有参考 |
| 同语言、同框架、跨项目 | 高 | 未做 |
| 跨语言 | 极高 | 未做 |

**建议**:先做「同一团队、多个仓库」。约定在同一团队内确实会复用,最有希望。

### Q5 界面展示什么?

| 选项 | 说明 |
|---|---|
| 知识卡列表 + 审核 | 当前已有 |
| 抽取过程可视化 | 项目 → 文件 → 事实 → 设计信号 → 卡 |
| 覆盖率 / 缺口 | 哪些行为还没被测试覆盖 |
| 迁移效果对比 | 用 / 不用知识的差异 |

**建议**:先做「项目路径 → 一键抽取 → 展示设计思路卡」这条主线,其他后续加。

### Q6 怎么判断一张知识卡有用?

| 选项 | 说明 |
|---|---|
| 人工审核 | 已有(verified) |
| 可执行验证 | 造「弄坏版本」,看卡的断言能不能抓住 |
| 历史缺陷验证 | 用真实修 bug 的提交,父版应失败、修复版应通过 |

**建议**:人审 + 可执行验证并行。人审判「该不该有」,执行验证判「断言有没有用」。

### Q7 支持范围?

**建议**:先把 Python / pytest 打透,再谈其他语言。当前适配器只覆盖 Python 和 Markdown。

## 6. 本周计划

不依赖 LLM 也能演示的部分优先:

1. **项目接入**:给定路径,自动扫出测试文件。
2. **设计信号**:确定性映射(参数化 / 异常 / mock / 边界 / fixture 依赖)。
3. **卡片 schema v2**:加 `applicability`(语言/框架/场景)和 `intent`(设计意图)。
4. **LLM 提炼器**:输入信号,输出意图,强制引用证据。
5. **界面**:项目路径 → 抽取 → 展示卡片。

第 1–3 步纯确定性,可单独测试和演示。

---

## 7. 需要验证的假设(风险)

1. **人写的测试里,是否真的有模型想不到的设计思想?** 如果大部分模型自己也能想到,迁移的价值需要重新评估。
2. **负迁移**:给一张不适用的卡,Agent 会不会变差?这个需要专门测。
3. **跨项目迁移**:单项目内的迁移和跨项目迁移难度差距很大,需要实测。

## 8. 术语

| 词 | 含义 |
|---|---|
| Evidence | 从文件里抄下来的原始事实 + 出处 |
| 设计信号 | 从事实确定性推出的「用了什么测试设计手法」 |
| 知识卡 | 一条可复用的知识(模式 + 条件 + 出处) |
| 适用条件 | 这张卡在什么项目/语言/框架/场景下成立 |
| 迁移 | 把一张卡用到别的项目/场景 |
| 可执行验证 | 把代码故意弄坏,看卡的断言能不能抓住 |
